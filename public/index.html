The turn

The model writes the test. The sandbox decides.

The coder model has no code tool. It reads the issue (on #6, with five reads through the workspace's GitHub MCP server), returns a Python script, and stops. Allowance checks the script, runs it with POST /code/execute, and reads only the result. A model that agrees with the reporter cannot turn a passing run into a reproduction.

How it decides

Five steps between an issue and a stamp.

  1. step01

    Screen

    The issue text goes to Otari with a guardrail attached. Our /validate service asks Qwen3Guard; a flagged issue gets 403 guardrail_violation, and neither triage nor the coder is called.

    qwen3guard-gen-8b
  2. step02

    Triage

    Llama 3.3 70B labels the issue and posts a welcome whose footer shows the contributor's balance.

    llama-3.3-70b-instruct
  3. step03

    Write

    On /repro, the routing policy sends the issue to Qwen3-Coder 480B Turbo, which may read the repository through GitHub MCP and returns a script. It cannot run code.

    policy allowance-coder
  4. step04

    Gate

    The script runs only if it installs the repository at a pinned commit, calls a function the issue names, and raises the marker on that call's result.

    lib/script-check.ts
  5. step05

    Run

    Reproduced needs a failed run whose stderr ends in the marker's AssertionError. Not reproduced needs return code 0 and NOT REPRODUCED last. Anything else is Inconclusive.

    POST /code/execute

Honest by design

What it does not do yet, in our own words.

Also in the README: tool results and images inside Otari's tool loop are not screened; spend can end slightly over the daily cap; a screenshot run can take about two minutes.

Questions a maintainer would ask

Does the model decide the verdict?

No. It writes a script and stops; it has no code tool. Allowance runs the script in Otari's sandbox and applies fixed rules to the result: return code, the exception that ends stderr, and the last line of stdout.

Who pays when a stranger comments /repro?

Their own Otari end-user allowance, $0.05 a day on the budget contributor-allowance. Owners, members and collaborators are charged to the repository pool. No one outside the project ever holds a key.

What stops a malicious issue?

The issue text is screened by Qwen3Guard through an Otari guardrail before triage or the coder sees it (#5 was blocked with a 403). Tool results and images inside Otari's tool loop are not screened. The verdict never depends on what MCP returned, and at most 300 characters of the final sandbox error are quoted back to the model.

What if the model writes a useless test?

A script that does not install the repository, call the named function and assert on its result is not run. A repair that changes the assertion is not run either: that is what happened on #7.

Is the screenshot fallback proven?

No. The policy lists Qwen3-VL as step 2, but on #6 the first target accepted the image, so nothing fell back. We say so in the README instead of claiming it.

Are the bugs real?

They are planted, in a small Python package written for the demo. The runs are real: every verdict is a public comment whose footer prints the Otari request id.

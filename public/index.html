The turn

The model writes the test. The sandbox decides.

The coder model has no code tool. It reads the issue (on #6, with five GitHub MCP calls), returns a Python script, and stops. Allowance checks the script, runs it with POST /code/execute, and reads only the result. A passing run can never be reported as Reproduced; the gate cannot tell whether the model's expectation is right.

How it decides

Five steps between an issue and a stamp.

  1. 01

    Screen

    The issue text goes to Otari with a guardrail attached. Our /validate service asks Qwen3Guard; a flagged issue gets 403 guardrail_violation, and neither triage nor the coder is called.

    flagged → 403, stop

    qwen3guard-gen-8b
  2. 02

    Triage

    Llama 3.3 70B labels the issue and posts a welcome whose footer shows the contributor's balance.

    llama-3.3-70b-instruct
  3. 03

    Write

    On /repro, the routing policy sends the issue to Qwen3-Coder 480B Turbo, which may read the repository through GitHub MCP and returns a script. It cannot run code.

    policy allowance-coder
  4. 04

    Gate

    The script runs only if it installs this repository, calls a function the issue names, and raises the marker on that call's result; Allowance then pins the install to the head commit.

    fails → not run

    lib/script-check.ts
  5. 05

    Run

    Reproduced needs a failed run whose stderr ends in the marker's AssertionError. Not reproduced needs return code 0 and NOT REPRODUCED last. Anything else is Inconclusive.

    POST /code/execute

What it does not do yet, in our own words.

Questions a maintainer would ask

Does the model decide the verdict?

No. It writes a script and stops; it has no code tool. Allowance runs the script in Otari's sandbox and applies fixed rules to the result: return code, the exception that ends stderr, and the last line of stdout.

Who pays when a stranger comments /repro?

Their own Otari end-user allowance, $0.05 a day on the budget contributor-allowance. Owners, members and collaborators are charged to the repository pool. Strangers never get a key; the app spends on their behalf.

What stops a malicious issue?

Qwen3Guard screens the issue text through an Otari guardrail before triage or the coder sees it; #5 got a 403, flagged as PII rather than injection, and the guard once passed the same text reframed as an error line. Tool results and images in the tool loop are not screened; at most 300 characters of the final sandbox error go back to the model.

What if the model writes a useless test?

A script that does not install the repository, call the named function and assert on its result is not run. A repair that changes the assertion is not run either: that is what happened on #7.

Is the screenshot fallback proven?

No. Qwen3-VL is step 2 of the policy, but on #6 the first target accepted the image, so nothing fell back.

Are the bugs real?

Planted, in a small Python package written for the demo. The runs are real: each verdict is a public comment with its Otari request id.
